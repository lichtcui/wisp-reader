## 1. 为什么旧的四方案不能直接沿用

初始那轮（A 就地重排 / B 页内分段 / C 可搜索列表+详情页 / D 设置页化）是在「13 条内置书源」的
假设下提出的。前提换成 3000 条之后：

| 旧方案 | 去留 | 理由 |
|---|---|---|
| **A 就地重排**（列表置顶 + 吸底操作栏 + `＋` 导入菜单） | 被吸收 | 骨架对（列表当主角、导入降级），但没回答 3000 条下「怎么找到目标源」和「检测作业住哪」 |
| **B 页内分段** | **采纳为布局 2** | 分段动机从「别挤在一起」升级为「检测是一个独立作业面」，理由更强 |
| **C 可搜索列表 + 详情页** | 部分采纳 | 搜索升级为必需品（采纳）；详情二级页未采纳（改用抽屉，见 §4.3） |
| **D 设置页化**（`GroupTitle` + `NavCell` 分组导航） | 退役 | 核心路径是「点进二级页才能改」——13 条时无所谓，3000 条时每次操作多两次跳转 |

## 2. 布局无关的共通决定（normative）

1. **搜索框必须在首屏可见。** 3000 条下「滚动查找」不成立；没有搜索的列表页等于没有界面。
2. **筛选器是主界面。** 默认视图已是筛过的（§3.2），不是 3000 行无差别列表。
3. **列表一律 `LazyForEach`**，只持 `SourceRow` 投影；过滤在内存做完再交给数据源
   （细节见 [`SPEC-SOURCE-LIST.md`](./SPEC-SOURCE-LIST.md)）。
4. **检测进度跨段常驻且跨页面存活。** 作业跑十数分钟到数十分钟，用户一定不在书源页；页内靠底部
   作业条，页外靠长时任务的系统通知（[`SPEC-DETECT-JOB.md`](./SPEC-DETECT-JOB.md)）。
5. **行内常驻检测态**（`可用 · 312ms`）。它同时是增量检测的输入（`last_detect_state` /
   `last_detect_at`），不是可选装饰。
6. **危险操作一律二次确认**；删除不再以品牌红主按钮出现在结果面首位。
7. **单源详情不做规则字段编辑**（v1 范围外，D10/D11）：只展示 + 改名称/地址/分组/启停/删除。
8. **不新增页面、不新增路由。** 段内切换不产生 `NavPathStack` 条目（与「选择来源 / 换源」同为
   页内形态）。`BottomDrawer` 的调用点数量保持 8 处不变。

## 3. 已定布局：两段式（书源 / 检测）

### 3.1 页面骨架

```
NavDestination('书源管理')
└─ Column
   ├─ SegmentedCell(['书源', '检测'])        ← components/ListCells.ets:79 现成组件
   ├─ 段内容（两段各自保留自己的滚动位置与状态）
   │   ├─ 书源段：搜索框 + 筛选条 + List(LazyForEach)
   │   └─ 检测段：范围条 + 作业卡 + 结果筛选条 + List(LazyForEach) + 批量动作
   └─ 底部作业条（跨段常驻，在段内容之外）
```

- 「＋ / ⋯」入口（导入、规则调试器、导出/恢复内置）放在标题栏或段选择器同排，**不再占据列表上方
  的空间**——现状 `pages/BookSourceManage.ets:518-574` 的导入区与「工具」组整块撤掉。
- 段切换不重建数据；两段共用 `SourceStore` 的内存投影，不重复查库。

### 3.2 书源段（详细）

```
┌ 书源管理 ────────────────  ＋  ⋯ ┐
│ [ 书源 ]          检测           │
│ 🔍 搜索名称 / 地址 / 分组         │
│ [全部 3000][启用 2712][停用 288] │   ← 筛选条，横滑
│ [未测 420][失败 156]             │
│ ──────────────────────────────── │
│ 笔趣阁8                  [●]  ⋯  │
│ 默认 · 可用 · 312ms              │
│ ──────────────────────────────── │
│ 起点中文                 [○]  ⋯  │
│ 正版 · 未测                      │
│         （LazyForEach）          │
│ ──────────────────────────────── │
│ 检测中 ● 1240/3000 · 预检        │
│ ▓▓▓▓▓▓▓░░░░░  约 8 分钟   [取消] │
└──────────────────────────────────┘
```

- **默认视图**：筛选条选中「启用」；排序按**三档**（已定 2026-10-14），档内按导入顺序：
  **需处理** = `不可用` → **待复查** = `未测`·`超时`·`无结果` → **正常** = `可用`。
  （为何分三档：`超时` 与 `无结果` 按 `SPEC-DETECT-UI.md` 的既有约定**不算坏源**，
  直接与 `不可用` 混在一档会误导用户去清理它们。档内权重可按实测调整，但「三档划分 +
  启用默认」两个性质不变。）
- **搜索**：防抖 150 ms，匹配 `name` / `url` / `group`，大小写不敏感。
- **筛选条**：`全部 N` / `启用 N` / `停用 N` / `未测 N` / `失败 N`（失败 = `unavailable`）。
  计数来自投影，一次算好，不在 `build` 里算。
- **行**：两行。上行 = 名称 + 开关 + `⋯`；下行 = `分组 · 检测态 · 耗时`。
- **分组**：由筛选条末端的「分组 ▾」切换（默认不分组）。分组开启时按 `bookSourceGroup` 分段，
  无分组归「默认」，组头显示组内条数与启用数。
- **点行** = 打开单源详情抽屉；**`⋯` 菜单** = 详情 / 停用（或启用）/ 删除；删除走确认弹窗。
- **空态**（搜索/筛选无结果，以及 0 条书源）必须有明确文案与出口（0 条时给「恢复内置」）。

### 3.3 检测段（详细）

```
┌ 书源管理 ────────────────  ＋  ⋯ ┐
│  书源            [ 检测 ]        │
│ 范围 [全部][未测 420][失败 156][分组▾]│
│ ──────────────────────────────── │
│ ● 运行中 · 预检 · 已用 3:12      │
│   1240 / 3000  ▓▓▓▓▓▓▓░░░  约 8 分钟│
│                          [ 取消 ] │
│ ──────────────────────────────── │
│ 结果 [全部][可用][无结果][超时][不可用]│
│ 起点中文      不可用 · 网络错误  ⋯ │
│ 番茄小说      无结果             ⋯ │
│ [ 关闭不可用 156 ]  [ 删除 156 ]  │
└──────────────────────────────────┘
```

- **范围条**：全部 / 未测 / 上次失败 / 分组 ▾；「当前筛选结果」「仅选中项」依赖 `source-list`
  的多选模式，**可后置**（见 `SPEC-SOURCE-LIST.md` 开放问题 5）。
  默认档是**增量**（未测 + 上次失败），不是全部。
- **作业卡**：三态（运行中 / 已完成 / 已取消）。运行中显示模式、已用时长、预计剩余、取消；
  已取消显示已得结果的条数与「继续」。
- **结果面**：按检测态筛选（维度与书源段**共用同一套**，不再定义第二套）；列表用 `LazyForEach`
  （现状抽屉里的 `ForEach` 必须换掉）；行尾 `⋯` 与书源段同一套操作。
- **批量动作**：关闭不可用 / 删除不可用，均为次级样式 + 二次确认 + 明确条数。
  仅 `unavailable` 参与——这条语义不许改（`SPEC-DETECT-UI.md` §「必须保留的语义」）。
- **判定口径说明**（「可用=完整链路通过；无结果=…」）改成按需展开，不再常驻。

### 3.4 底部作业条（跨段常驻）

| 状态 | 显示 | 点击 |
|---|---|---|
| 从未检测 | `检测书源…` | 切到检测段并展开范围选择 |
| 运行中 | `● 1240/3000 · 预检` + 进度 + `[取消]` | 切到检测段 |
| 已完成 | `检测完成 · 可用 2712 / 不可用 156` | 切到检测段看结果 |
| 已取消 | `已取消 · 已测 1240 / 3000` | 切到检测段，给「继续」 |

离开书源页时作业条不在；页外可见性由长时任务的系统通知承担（用户点击通知可回到本页）。

## 4. 未采纳的候选（记录）

**4.1 布局 1 — 搜索优先单页 + 常驻作业条。** 一个页面承载全部，检测压成底部条，结果面挤在
`BottomDrawer` 里。优点：文件最少、与现有 UI 语言最一致。未采纳原因：3000 条的结果面是**与书源
列表同量级**的第二个大列表，塞进抽屉后筛选条 + 列表 + 批量动作的纵向空间不足，且抽屉的滚动与
书源列表的滚动容易混淆。

**4.2 布局 3 — 书源库 + 作业中心（两个二级页）。** 检测作业与单源详情各自是 `NavDestination`。
职责最干净，两个大列表各自独占一屏，作业页可从任意处进入。未采纳原因：代价是 2 个新页 + 路由
（约 10 行）与每次操作多一跳；本次的诉求是「把 3000 条跑通」而不是长期扩展，段内切换已能容纳
两个面。**若后续要加检测历史、书源分组管理、规则调试整合，这条是自然演进方向**——届时从布局 2
拆出作业页是增量动作，不是返工。

**4.3 单源详情为何用抽屉而非二级页。** 详情内容量小（名称/地址/分组/启停/最近检测/规则字段只读
展示 + 删除），抽屉足够；且复用现成的第 6 处 `BottomDrawer` 调用点，`UI-SPEC` 只需改一行描述。
