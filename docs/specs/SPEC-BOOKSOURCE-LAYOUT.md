## 1. 为什么旧的四方案不能直接沿用

初始那轮（A 就地重排 / B 页内分段 / C 可搜索列表+详情页 / D 设置页化）是在「13 条内置书源」的
假设下提出的。前提换成 3000 条之后：

| 旧方案 | 去留 | 理由 |
|---|---|---|
| **A 就地重排**（列表置顶 + 吸底操作栏 + `＋` 导入菜单） | 被吸收 | 骨架对（列表当主角、导入降级），但没回答 3000 条下「怎么找到目标源」和「检测作业住哪」 |
| **B 页内分段** | **已退役（2026-11-02）** | 当时的分段动机（「检测是独立作业面」）仍成立，但落地成了「两个页面挤在一个屏幕」：段选择器 + 两套搜索/筛选/分组 + 底部作业条，同一个进度有两份、搜索框有两个。改为**任务态切换**（§3.3）后不再需要段 |
| **C 可搜索列表 + 详情页** | 部分采纳 | 详情二级页未采纳（改用抽屉，见 §4.3）；**搜索已于 2026-11-02 撤掉**（§7） |
| **D 设置页化**（`GroupTitle` + `NavCell` 分组导航） | 退役 | 核心路径是「点进二级页才能改」——13 条时无所谓，3000 条时每次操作多两次跳转 |

## 2. 布局无关的共通决定（normative）

1. ~~**搜索框必须在首屏可见。**~~ **已撤（2026-11-02）**：本页不提供搜索，见 §7「已知代价」。
2. ~~**筛选器是主界面。**~~ **已撤（2026-11-02）**：本页不提供筛选；默认视图即全量列表，靠排序把待处理的源置顶。
3. **列表一律 `LazyForEach`**，只持 `SourceRow` 投影；排序在内存做完再交给数据源
   （细节见 [`SPEC-SOURCE-LIST.md`](./SPEC-SOURCE-LIST.md)）。
4. **检测进度跨页面存活，但只在一个地方显示。** 作业跑十数分钟到数十分钟，用户一定不在书源页；
   页内靠**任务态**（整页进度卡），页外靠长时任务的系统通知（[`SPEC-DETECT-JOB.md`](./SPEC-DETECT-JOB.md)）。
5. **行内常驻检测态**（`可用 · 312ms`）。它同时是增量检测的输入（`last_detect_state` /
   `last_detect_at`），不是可选装饰。
6. **危险操作一律二次确认**；删除不以品牌红主按钮出现在首位。
7. **单源详情不做规则字段编辑**（v1 范围外，D10/D11）：只展示 + 改名称/地址/分组/启停/删除。
8. **不新增页面、不新增路由。** 任务态切换不产生 `NavPathStack` 条目（与「选择来源 / 换源」同为
   页内形态）。`BottomDrawer` 的调用点数量保持 8 处不变。

## 3. 已定布局：单一主体 + 任务态（2026-11-02）

### 3.1 页面骨架

```
NavDestination('书源管理')
└─ Column
   ├─ 页内头行 48vp：左「N 个书源 · M 启用」，右单一 `⋯` 功能键   ← 任务态下整行不渲染
   ├─ 「从链接导入」触发时临时出现的 URL 输入条（导入成功即收起）
   ├─ 结果提示卡（仅导入 / 导出 / 清理有话要说时出现）
   ├─ Stack(layoutWeight 1)
   │   ├─ 书源列表（`LazyForEach`；任务态下 `Visibility.Hidden`）
   │   └─ 检测进度卡（任务态下 `Visibility.Visible`）
   └─ BottomDrawer(书源详情)  ← 常驻挂载，调用点仍为 8 处
```

- 页面主体只有**一个**：书源列表。页面级工具栏只剩头行上那一个 `⋯`。
- 「任务态」= 检测进行 / 结束的那一屏；它由 `detectView` 这一页内状态驱动，不是第二个 tab、不是新路由。
- 列表在任务态下用 `Visibility.Hidden` 保留挂载（不卸载），返回时滚动位置不丢。

### 3.2 书源列表（详细）

```
┌ 书源管理 ────────────────   13 个书源 · 12 启用    ⋯ ┐
│ 笔趣阁8                                  [●]  ⋯  │
│ 默认 · 可用 · 312ms                                │
│ ────────────────────────────────────────────────── │
│ 起点中文                                 [○]  ⋯  │
│ 正版 · 未测                                        │
│                （LazyForEach）                      │
└────────────────────────────────────────────────────┘
```

- **排序**：三档（已定 2026-10-14），档内按导入顺序：
  **需处理** = `不可用` → **待复查** = `未测`·`超时`·`无结果` → **正常** = `可用`。
  （为何分三档：`超时` 与 `无结果` 按 `SPEC-DETECT-UI.md` 的既有约定**不算坏源**，
  直接与 `不可用` 混在一档会误导用户去清理它们。）
- **无搜索、无筛选条、无分组选择器。** 列表是平的；分组信息仍在行内第二行展示。
- **行**：两行。上行 = 名称 + 开关 + `⋯`；下行 = `分组 · 检测态 · 耗时`。
- **点行** = 打开单源详情抽屉；**行尾 `⋯`** = 详情 / 停用（或启用）/ 删除；删除走确认弹窗。
- **空态**（0 条书源）：文案 + 「导入书源」主按钮 + 「恢复内置」次按钮——空库时导入就是当前主任务，
  不能让人去 `⋯` 里翻。

### 3.3 检测任务态（详细）

```
┌ 书源管理（页内头行不渲染）──────────────────────┐
│                                                  │
│        ● 检测中 · 完整检测            03:12       │
│        ▓▓▓▓▓▓▓░░░░░░░  1240 / 3000               │
│        后台继续运行               预计剩余 08:20  │
│        [            取消检测            ]        │
│                                                  │
└──────────────────────────────────────────────────┘
```

- **入口（全部在 `⋯` 里，计数写进菜单项，故不需要二级范围选择器）**：
  - `检测书源（增量 N）` → `probe`（L1 预检）。N = 未测 + 上次失败 + 7 天未检的启用源；N = 0 时该项禁用。
  - `全部重测（M）` → `full`。M = 启用源总数；M = 0 时该项禁用。
- **进行中**：整页只有进度卡（`components/DetectProgressCard.ets`）：状态点 + 「检测中 · 预检/完整检测」+
  已用时长 / 已完成 / 总数 / 进度条 / 预计剩余 / 后台态 + **取消**（点击后进「正在停止…」）。
- **结束**（`done` / `cancelled` / `failed`）：进度卡**原地**变成摘要 + 主按钮，不跳页：
  - `done`：`本轮已检测 N 个书源；当前 U 个不可用，已排到列表最前。` + 「返回书源列表」；
    `U > 0` 时追加次级按钮「关闭不可用 U」「删除不可用 U」（`unavailable` 才参与，语义见
    [`SPEC-DETECT-UI.md`](./SPEC-DETECT-UI.md)「必须保留的语义」）。
  - `cancelled` / `failed`：错误信息或「已保留本轮结果」+ **固定双按钮** `[继续本轮][返回书源列表]`；
    「继续本轮」在 `canResume` 转真前置灰。`canResume` 要等 `runningTask` 释放后才为真（真机实测约 1s），
    若按它切换布局，按钮位置会在取消后跳一次（全宽 `[返回书源列表]` → 双按钮），用户可能误点到「继续本轮」。
- **列表本身就是结果视图**：`done` 之后失败源已按 §3.2 的排序浮到最前，**不再有第二个结果列表**，
  也不再需要「结果筛选条」。
- **冷启动**：只有 `DetectJobRunner.status === running` 才进任务态；已完成 / 已取消的历史轮次不占屏。
- **任务态下头行不渲染**（连 `⋯` 一起）——检测中不提供导入 / 导出 / 再次检测，避免改源集与冻结的作业范围打架。

### 3.4 底部作业条 → **已删除（2026-11-02）**

旧版有「跨段常驻的底部作业条」，与检测段的作业卡同时表达同一份进度（同一个作业两个显示面）。
改为任务态后，进度卡是唯一显示面，底部作业条整块撤掉。页外可见性仍由长时任务的系统通知承担。

## 4. 未采纳的候选（记录）

**4.1 布局 1 — 搜索优先单页 + 常驻作业条。** 一个页面承载全部，检测压成底部条，结果面挤在
`BottomDrawer` 里。优点：文件最少、与现有 UI 语言最一致。未采纳原因：3000 条的结果面是**与书源
列表同量级**的第二个大列表，塞进抽屉后筛选条 + 列表 + 批量动作的纵向空间不足，且抽屉的滚动与
书源列表的滚动容易混淆。（2026-11-02 改版后「常驻作业条」这一半被反向采纳：页面主体确实是列表，
但检测改成**整页任务态**而不是底部条。）

**4.2 布局 3 — 书源库 + 作业中心（两个二级页）。** 检测作业与单源详情各自是 `NavDestination`。
职责最干净，两个大列表各自独占一屏，作业页可从任意处进入。未采纳原因：代价是 2 个新页 + 路由
（约 10 行）与每次操作多一跳。**若后续要加检测历史、书源分组管理、规则调试整合，这条是自然演进方向。**

**4.3 单源详情为何用抽屉而非二级页。** 详情内容量小（名称/地址/分组/启停/最近检测/规则字段只读
展示 + 删除），抽屉足够；且复用现成的第 6 处 `BottomDrawer` 调用点，`UI-SPEC` 只需改一行描述。

## 7. 2026-11-02 改版：为什么撤掉搜索 / 筛选 / 分段 / 底部作业条

**触发**：真机使用反馈——「书源管理 UI 混乱」。诊断的根因不是控件多，而是**同一个问题有多个状态源**：
「我在看什么」被段选择器、筛选 chips、底部作业条三处重复表达，搜索框出现两次（书源段一次、
检测结果面一次），同一份检测进度有两份（检测段作业卡 + 底部作业条）。

**改版**：页面主体收敛为书源列表；页面级动作全部进 `⋯`；检测改为任务态（§3.3）；
搜索 / 筛选 chips / 分组选择器 / 底部作业条整块撤掉。

**为什么要撤（而不是保留着改成更好看）**：

- 主体唯一：屏幕上只该有一个「当前对象」。列表在常态下就是那个对象，检测进行时进度卡是那个对象，
  二者由 `detectView` 互斥，不存在第三种表达。
- 入口唯一：页面级动作（低频、批量、破坏性）进 `⋯`，行级动作（开关/详情/删除）留在行上——
  判据是**作用域**与**频率**，不是「能不能塞进顶栏」。
- 能力不丢：撤掉的结果面连带删掉「关闭/删除不可用」，该能力搬到摘要卡（检测刚结束时正是它最有用的时候），
  仍走 `setEnabledMany` / `removeMany` 批量事务与二次确认。

**已知代价（接受）**：

1. **3000 条下没有搜索**，只能滚动查找。行内仍有 `分组 · 检测态 · 耗时`，且待处理源排在最前，
   但目标定位能力确实弱于 2026-10-14 版。若要恢复，最小形态是**头行加一个搜索图标**（点开才出输入框），
   不改变 §3.1 的骨架。
2. **没有筛选**，因此看不到「只看失败源」这类视图；`done` 之后靠排序把 `unavailable` 置顶代偿。
3. **不能按分组批量检测**（原范围条的分组档）。分组选择器撤掉后，`probe` 范围的粒度是整库。

**改版后的真机验收（2026-11-02，debug `33Z0224424136564`）**：

- 常态：头行 `13 个书源 · 13 启用` + 列表 + `⋯`。对 `dumpLayout` 做反例扫描——
  `搜索名称` / `全部 N` / `启用 N` / `停用 N` / `未测 N` / `失败 N` / `显示 N /` / `分组 ·` 全部 **0 命中**，
  且旧符号（`sourceRowMatchesQuery` / `SegmentedCell` / `ManageFilterChip` / `jobBar`）在编译产物里归零。
- `⋯` 菜单 = 设计的 7 项（debug 包 8 项，多 `T1.6 性能造数（3000）`）；`检测书源（增量 2）` /
  `全部重测（13）` 的计数与头行 `13 个书源 · 13 启用` 对得上。
- `检测书源（增量 2）` → 整页只剩进度卡：`检测完成 · 预检 | 2 / 2 | 本轮已检测 2 个书源；当前 2 个不可用，
  已排到列表最前。| 返回书源列表 | 关闭不可用 2 | 删除不可用 2`（列表与头行都不再渲染）。
- `全部重测（13）` → `检测中 · 完整检测 | 0 / 13 | 后台继续运行 | 取消检测`；取消 → `已取消 · 0 / 13` +
  固定双按钮（`继续本轮` 先置灰、约 1s 后转可用，两次 dump 的**按钮边界完全一致**）。
- 点「返回书源列表」→ 回到列表，头行与 13 行原样；全程 hilog 无 JS/ArkTS 异常。

**已知语义（非缺陷）**：取消后同范围再点「全部重测」= **续跑同一轮**（`startDetectJob` 的 `canResume`
分支保留 `startedAt` 与结果文件），所以已用时长会接着上一段累计，而不是从 00:00 重新计时。这与
「已完成结果不丢」是同一个设计。
