# 远程 TTS 引擎选型与「杂音」根因（T-TTS 系列）

> 背景：远程听书（VPS 上的 sherpa-onnx）被反馈三个问题，按出现顺序 —— **朗读跟不上（RTF）**、**大量杂音**、**发音像日本人**。
> 本文记录症状定位、已实施的修复、各引擎在本机（4C Xeon 8173M / 3.9G）上的**实测**数据，以及最终上线的 VITS 方案与它踩到的三个真 bug。
> 部署与运维细节见 [`../remote-tts-deploy.md`](../remote-tts-deploy.md)；早期调研见 [`TTS-PLAN.md`](./TTS-PLAN.md)。

## 0. 结论先行

1. **ZipVoice 在这台 4C 机上无解**：`num_steps` 是唯一能压住「杂音」的旋钮，但 `steps=6` 的 RTF 已达 **1.485**，而 `steps=2/3`（RTF 0.56/0.83）一律浑浊。**"实时"与"干净"在 ZipVoice 上互斥** —— 这是换引擎的根本理由，不是调参问题。
2. **引擎已换成 VITS**（`vits-hf-zh-jp-zomehwh.onnx`，804 说话人，原生 22050 Hz），线上实测 **RTF 0.576**、RSS ≈ 300MB、**长段落不掉速**。
3. **音色没有花钱微调**：这个 804 说话人底模里**自带 64 个原神声线**（含钟离/胡桃/甘雨/刻晴/雷电将军/八重神子/可莉/派蒙…），F0 分布正常（男 118–139 Hz、女 208–312 Hz）。原先规划的「微调 VITS」整条路线**作废**。
4. **真正花时间的不是引擎，是三个上游坑**：
   - **词典**：模型自带 lexicon 是「中文单字表 + 日文词表」两遍拼接，**没有一个中文词组** → 多字词全部吃日文读音（`追求` 读成 ついきゅう）。这是「像日本人说话」的唯一原因。
   - **`rule_fsts`**：模型符号表没有 0-9，不加载 `date/number/phone.fst` 时**数字被整段静默丢弃**（`第2024章` → `第章`）。
   - **停顿**：sherpa 句间只插 ~80ms 静音，`silence_scale` 调不动 → 改为**服务端自己切句 + 自插 320ms**。
5. **客户端零改动**：服务器仍出 24kHz S16LE mono RIFF，且旧音色名（流萤/花火/卡芙卡）作为别名保留。

## 1. 症状一：「杂音」到底是什么

对合成音频与参考音频做逐频段能量占比（`app.py` 的 `_profile()`，哈宁窗 + 分带求和）：

| 候选病因 | 实测值 | 判定 |
|---|---|---|
| 低频隆隆声（0–120Hz） | 合成 **0.0%** / 参考 0.0% | ✗ 排除 |
| 直流漂移 | ~0.00005 | ✗ 排除 |
| 削波失真 | 0% 采样点 | ✗ 排除 |
| 高频嘶声（>10kHz） | 0.02–0.46% | ✗ 排除 |
| **200–300Hz 过量 + 600–1500Hz 缺失** | **合成 47.3% / 7.8%，参考显著更均衡** | ✓ 机制已定位 |

**机制**：ZipVoice 是 flow-matching 零样本克隆模型，`num_steps` 决定 ODE 求解精度。步数不足时高频细节未被复原，能量堆积在低频共振峰 —— 不是"加了噪声"，而是"该有的高频没生成出来"。

> ⚠️ 这条指标后来发现**被 F0 污染**，不能单独当证据，见 §6。但 ZipVoice 的浑浊本身是真实听感，用户反馈与上表一致。

## 2. 步数 ↔ RTF ↔ 音质（实测，卡芙卡，VPS 4C）

| `NUM_STEPS` | RTF | 200–300Hz | 600–1500Hz | 评价 |
|---|---|---|---|---|
| 2 | **0.558** | 47.3% | 7.8% | 快但很浑浊 |
| 3 | **0.834** | 47.8% | 12.1% | 仍是浑浊，余量已只剩 1.2× |
| 6 | **1.485** | 35.2% | 18.4% | 音质可接受，**但已不能实时** |
| 12 | **2.943** | — | — | 不可用 |

**结论：在这台机器上，ZipVoice 没有任何一档配置能同时做到「实时」与「不浑浊」。** 这是架构约束，不是参数调优问题。

## 3. 症状二：RTF 与内存（ZipVoice 时期的 v1.1.0 管线）

`server/app.py` v1.1.0 在推理之后串了一条纯 numpy 后处理链（VPS 上**没有 scipy / soundfile / ffmpeg / sox**，一切都得自己实现）：

| 环节 | 实现 | 目的 |
|---|---|---|
| `_resample_fft()` | 加载时把参考音频一次性重采样到 24kHz | 消除**每请求**新建 44.1k→24k 重采样器（老版本 6 天长到 2.5GB 的元凶） |
| `_eq()` | 零相位 FFT RBJ peaking EQ：`280Hz -3.5dB Q0.9` + `2800Hz +3.5dB Q0.7` | 去浑浊 + 补临场 |
| `_limit()` | 分块峰值限制器，包络用**膨胀（±2 块取最大）**而非均值 | 防限幅后的增益回弹（均值平滑曾让花火峰值冲到 1.000） |
| `_normalize()` | 归一到 `TARGET_RMS_DBFS=-18`，天花板 `-1 dBFS` | 统一响度 |
| `_fades()` | 15ms 淡入 / 40ms 淡出 | 去头尾爆音 |

**实测效果**：卡芙卡 200–300Hz 35.4%→**24.3%**；长文 204 字 42.7%→**32.1%**；花火 17.1%→**9.2%**。响度一致性 **5.5 dB → 0.62 dB**，全部 **0% 削波**。

> **v2.0.0 保留全部环节，但默认关掉 EQ**（`EQ_BANDS=""`）：EQ 是给 ZipVoice 打的补丁，VITS 不需要。响度归一 / 限幅器 / 淡入淡出照常运行。

**内存**：老版本运行 6 天后 RSS **2513MB**（新起 + 8 请求 766MB），根因是每请求重建重采样器（44.1k→24k ≈ 2.2 MB/次 × 800 次 ≈ 1.75 GB）。v1.1.0 修掉后做 **150 次同文本 soak** 增量仍 ~1.5 MB/次，于是做了**干净的 100 次 soak**（排除输入长度变量）：

```
clean soak start rss=354636 kB
  req=20  rss=441188 kB   ← 首次 warmup，ONNX arena 一次性高水位
  req=40  rss=441124 kB
  req=100 rss=441124 kB
  静置 60s 后 rss=441124 kB   ← 零增长
```

→ **无逐请求泄漏**；354→441MB 是一次性 arena 高水位。"6 天涨 1.75GB" 确证为已修的 per-request 重采样器。

### 4.1 音色：804 说话人预导模型，**不需要微调**

同一份 804 说话人配置（`lkz_G_CJ.json`）下先后试了两个 ONNX，结论差别极大：

| 文件 | 男声 F0（钟离/魈/迪卢克） | 女声 F0 分布 | 判定 |
|---|---|---|---|
| `theresa.onnx`(121,913,906 B) | **190.1 / 219.4 / 215.0 Hz** ← 男声落在女声区 | 全部挤在 **305–360 Hz** | ✗ **坏文件，已弃用** |
| `vits-hf-zh-jp-zomehwh.onnx` | **122.4 / 139.4 / 118.5 Hz** ✓ | 208–390 Hz，区分度正常 | ✓ **采用** |

`vits-hf-zh-jp-zomehwh` 实测 F0（原生 22050 Hz）：钟离 122.4 / 魈 139.4 / 迪卢克 118.5 / 雷电将军 207.8 / 八重神子 251.0 / 刻晴 255.1 / 甘雨 272.9 / 胡桃 312.0 / 派蒙 343.7 / 可莉 390.0 Hz。

> F0 估计器已用真值校准：`vits-zh-ll` spk1 = 89.4/104.1 Hz、spk4 = 101.9/114.9 Hz（真男声，正确测出）；ZipVoice 流萤 259.5 Hz。**估计器无倍频错误，上表可信。**
> 两个文件是**同一份 speaker 映射**（sid 索引 = `lkz_G_CJ.json` 的 `speakers` 数组下标），所以「theresa 音高不对」是文件本身坏了，不是映射错。

**sid 核定表**（部分，完整见 `/tmp/lkz_G_CJ.json`）：

| 角色 | sid | 角色 | sid |
|---|---|---|---|
| 钟离 | 104 | 胡桃 | 119 |
| 魈 | 101 | 甘雨（椰羊） | 111 |
| 迪卢克 | 94 | 刻晴 | 115 |
| 可莉 | 103 | 雷电将军（雷神） | 125 |
| 派蒙 | 551 | 八重神子（神子） | 133 |
| 夜兰 | 135 | 神里绫华（龟龟） | 87 |
| 优菈 | 124 | 纳西妲（草神） | 142 |
| 枫原万叶（万叶） | 120 | 珊瑚宫心海（心海，扣扣米） | 127 |

> 注意：**带昵称后缀的条目才是命中项**（`甘雨（椰羊）`、`雷电将军（雷神）`、`神里绫华（龟龟）`…），直接搜 `甘雨` 会落空。

### 4.2 症状三：「像日本人说话」= 词典 bug

模型自带的 `zome_lexicon.txt`（36,787 行 / 782 KB）是**两遍拼接**、每遍按 Unicode 码点排序：

| 段 | 行数 | 内容 |
|---|---|---|
| pass 1 | 21,287 | 中文**单字**表（覆盖 0x4E00–0xFA6C）—— **没有任何中文词组** |
| pass 2 | 15,500 | **日文词表**（`セクシー` `モニタ` `追求` `統一` `観る`…） |
| 重合 | 1,350 | 同时出现在两段的词 |

sherpa 的 `InitLexicon` **保留首次出现**（另 1,376 条日文重复项会打 `Duplicated word … Ignore it`），所以重合词的中文读音是对的。**但 14,150 个「只在 pass 2」的词会被读成日文** —— 而且**不打任何警告**：

| 词 | `zome_lexicon.txt` | theresa 的 `lexicon.txt` |
|---|---|---|
| **追求** | `ʦ ɯ ↑ i k y ɯ ɯ` = **ついきゅう** ❌ | `ʦ ` ⁼ w e i → ʧ ʰ y o u ↑` = **zhuīqiú** ✓ |
| **分裂** | `b ɯ ↑ N r e ʦ ɯ` = **ぶんれつ** ❌ | `f ə N N → l y e ↓` = **fēnliè** ✓ |
| 中国 | `ʦ ` ⁼ u N g → k ⁼ w o ↑` ✓（重合，中文胜出） | 同 |
| 翻涌 / 安宁 / 许多 / 一个 / 我们 | **整词缺失** → 只能逐字拼 | 全有 ✓ |

**修法**：`lexicon_final.txt` —— 用**纯中文**的 `lexicon.txt`（66,395 条 = 20,901 单字 + 45,494 词组，`sort -u` 后零重复）打底，再补 395 个 pass 1 里的罕用扩展单字，**日文段整段丢弃**。加载警告：**重复 0 / OOV 0**。

> 可互换性已验证：两份 `tokens.txt`（`zome_tokens.txt` vs `tokens.txt`）**`diff` 完全一致**（都 268 B，同一套 52 符号表），所以换词典不会破坏 phoneme→id 映射。
> 生成脚本：`/root/tts/genshin-vits/mklex2.py`（按码点回绕点自动切 pass 1/pass 2，别手工数行号）。

### 4.3 数字被整段吞掉 = 缺 `rule_fsts`

模型符号表里**没有 0-9**。不加载 FST 时：

```
第2024章 他有3个苹果，花了12.5元，电话是13800138000。
→ Ignore OOV '2024' / '3' / '12' / '5' / '13800138000'   实际念成「第章 他有个苹果，花了元，电话是。」
```

修法是 `OfflineTtsConfig(rule_fsts="date.fst,number.fst,phone.fst")`（文件在 `/root/tts/vits-zh-ll/sherpa-onnx-vits-zh-ll/`）。**实测该句时长 3.31s → 6.59s**，即数字确实被展开成中文读出来了。

> `new_heteronym.fst` 测了**没有任何差别**（那是 `vits-zh-ll` 自己的多音字表，与本模型不匹配），不要加载。
> 副作用：加载 FST 后残留 OOV 从每次几十条降到 1 条（就剩全角冒号 `：`）。

### 4.4 句末停顿只有 80ms = 服务端自己切句

实测（112 字段落，钟离）：

| 输入 | 时长 | 内部停顿 |
|---|---|---|
| 保留标点 | 21.47s | 9 处，均 **0.08s**，最长 0.14s |
| **去掉标点** | 19.04s | **0 处** |

→ **标点驱动 sherpa 的分句与停顿，绝不能清掉**；但 sherpa 在句间只肯插 ~80ms 静音，**且 `silence_scale` 在 VITS 路径上完全无效**（0.2→1.0 输出时长一字不差；`max_num_sentences` 同样几乎无影响）。80ms 的句末停顿听起来就是「没有呼吸感 / 语速怪」。

**修法**：`app.py` 的 `_split_sentences()` 按 `。！？!?…` 与换行切句，逐句合成后**自己插 `SENTENCE_PAUSE_MS=320` 静音**；逗号留在段内，沿用模型自己的短停顿（实测 0.06–0.21s）。

长段落实测停顿结构：**0.41 / 0.50 / 0.49s（句末）+ 0.06–0.21s（逗号）**。

### 4.5 上线实测

`POST /tts` 端到端（`speed:1.0` → `SPEED_SCALE=0.85`）：

| 用例 | 采样率 | 时长 | RTF | 响度 | 峰值 | 削顶 |
|---|---|---|---|---|---|---|
| 陷阱句（20 字） | 24000 ✓ | 3.56s | 0.656 | −18.0 dBFS | 0.84 | 0% |
| 数字句（37 字） | 24000 ✓ | 7.15s | 0.583 | −18.0 dBFS | 0.89 | 0% |
| **长段落（123 字 / 4 段）** | 24000 ✓ | 22.96s | **0.576** | −18.0 dBFS | 0.89 | 0% |
| 旧名别名（流萤→甘雨） | 24000 ✓ | 1.56s | 0.613 | −18.0 dBFS | 0.48 | 0% |

对照 ZipVoice `steps=3` 的 0.834，**RTF 降低 31%，且长段落不再掉速**（ZipVoice 长文 0.843）。
**硬约束 RTF < 1 达标。** 客户端契约（24000 Hz S16LE mono RIFF）不变。

> 语速：`SPEED_SCALE`（默认 0.85，映射到 sherpa 的 `length_scale = 1/speed`）。VITS 的 `speed` 是**真·语速控制**，而 ZipVoice 时期 `speed` 是空转的（服务端注释原文："ZipVoice has no rate control"）。实测段落 ~325–368 字/分 @ speed 0.85。

## 5. 引擎矩阵（本机实测 / 硬约束筛选）

硬约束：**① 必须中文；② 必须能拿到角色音色；③ 4C/3.9G 上 RTF < 1 且有余量。**

| 引擎 | 中文 | 角色音色 | 本机实测 RTF | 判定 |
|---|---|---|---|---|
| **sherpa-onnx VITS（804 说话人）** | ✓ | **✓ 自带 64 个原神声线** | **0.576** | ✓ **已上线** |
| sherpa-onnx VITS（`vits-zh-ll`） | ✓ | 固定 5 说话人 | 0.398–0.431 | 同架构备选 |
| ZipVoice | ✓ 中英 | 零样本克隆 ✓ | 0.834 (steps=3) / 1.485 (steps=6) | ✗ 实时与干净互斥 |
| `vits-melo-tts-zh_en` | ✓ 中英 | 固定 1 说话人 | （未测） | 同族备选 |
| Kokoro / Matcha / Supertonic 3 | 部分 | 固定音色 ✗ | — | ✗ 无角色音色 |
| PocketTTS | **✗ 无中文** | 零样本克隆 ✓ | — | ✗ 语言不支持 |
| Bert-VITS2 | ✓ | 可训练 | — | ✗ 需 1.3B BERT 前端，4C/4G 不可能 |
| **GPT-SoVITS** | ✓ | **最好，且已有成品模型** | 未测 | ✗ 需要 torch + 自回归 GPT 解码，4C/4G 上 RTF 大概率 ≫1，**与"必须 RTF<1"直接冲突** |

**关键洞察**：市面上给原神/崩铁角色配音色的成品权重几乎都是 **GPT-SoVITS / Bert-VITS2 格式**（`.ckpt`/`.pth`）—— 音色最好，但推理栈太重。而 **VITS 是唯一"轻到能在 4C 上跑进 RTF 0.6"且"已经有现成角色声线"的架构**。上一版结论是「愿意为音色花一次微调」，实际发现**连微调都不用花**（§4.1）。

## 6. 方法论修正：「200–300Hz 占比」被 F0 污染

§1/§2 用「200–300 Hz 能量占比过高」指认浑浊，**这个指标本身不可靠**：它同时受**基频位置**影响。

| 声音 | F0 | 200–300Hz 占比 | 解读 |
|---|---|---|---|
| 钟离（男） | 122 Hz | 22% | 能量主要落在 0–120Hz（7–14%） |
| 甘雨 / 雷电将军 / 八重神子 | 220–260 Hz | **50–63%** | F0 就在该带里，占比高是**必然**，与浑浊无关 |
| ZipVoice 流萤 | 259 Hz | — | 同理 |

**正确用法**：
- 该指标只能用于**同一说话人、同一文本**的 A/B（同 F0 基准），不能跨音色比较 —— 本文 §1 的 ZipVoice 结论属于前者，有效。
- 判断男声是否正常，**看 F0 绝对值**最直接：男声应在 **90–140 Hz**。`theresa.onnx` 的男声落在 190–220 Hz，这才是它的致命伤（§4.1）。
- 跨音色的响度和削顶用 **RMS + peak + 削顶率**，不要用分带占比。

## 7. 残余风险（与文件位置）

| 风险 | 证据 | 处置 |
|---|---|---|
| **客户端 60s 超时会在播放中换音色** | `RemoteTtsClient.ets` `readTimeout=60000`；`AHEAD_REMOTE=3`（`Const.ets:58`）+ 服务端 `_lock` 串行 → 第 3 个排队请求最坏 ≈87s > 60s → 触发 `fallbackToSystem()` 中途切成系统 TTS | 建议把 `readTimeout` 提到 ≥120000。**设备离线，未改 ArkTS**。换引擎后 RTF 0.576，最坏排队从 ~87s 降到 ~57s，**已回到阈值以内但无余量** |
| App 端音色列表还是旧的 | `Const.ets` `TTS_REMOTE_VOICE_OPTIONS=[流萤,花火,卡芙卡]` | 服务端做了别名映射，App 不改也能播；待设备可用时替换为 5 个新名 |
| 段落未按长度切分 | `BookContent.ets:20` 仅按 `\n` 切行 | 服务端已按标点切句并限长，暂不动客户端 |
| 崩铁角色音色不存在 | VITS 系无 HSR 数据 | 已改用原神音色（用户确认） |
| 罕用字仍可能 OOV | 词典为简体常用字 + 词组 | 残留 OOV 实测 1 条/请求（全角冒号 `：`，不影响听感） |

## 8. 内存与稳定性

- **swap**：已加 2G `/swapfile` + `vm.swappiness=10` + `vm.vfs_cache_pressure=50`（原 3.9G 无 swap，曾导致 `rustc` 构建被 OOM 杀掉）。
- **VITS 内存**：加载 196→**317 MB**，soak 后稳定在 **441 MB**（含 arena 高水位），**100 次请求零增长**（§3 的 clean soak）。
- **systemd 加固**：`MemoryHigh=1200M` / `MemoryMax=1600M` / `RuntimeMaxSec=86400`（每日重启）+ `MALLOC_ARENA_MAX=4` / `MALLOC_TRIM_THRESHOLD_=65536`。目标是"万一回归就把 `tts` 自己重启掉"，而不是让内核 OOM 去杀别的进程。换到 VITS 后余量充裕（441MB vs 1600MB），**重启成本从 ~7s 降到 ~3s**。
