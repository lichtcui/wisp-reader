## 证据 1：DATA_TRANSFER 长时任务可申请、通知栏出现常驻通知

```
10-15 07:40:32.725 63383 SourceReaderProbe: T0.1 start ok mode=DATA_TRANSFER
```
通知栏截图 OCR：`源阅读 / 正在运行数据传输任务，删除通知后任务.…`（系统常驻通知，与本项目 TTS 的
`audioPlayback` 通知同款）。**结论：`BackgroundMode.DATA_TRANSFER` 在 SDK 与真机上都存在且可申请。**

## 证据 2：一个 Ability 同时只能持有一个长时任务 → `9800005`

TTS 正在播放（已持 `AUDIO_PLAYBACK`）时申请 `DATA_TRANSFER`：

```
10-15 07:43:52.841 63383 SourceReaderProbe: T0.1 start fail code=9800005
  msg=BussinessError 9800005: Continuous Task verification failed. The application has applied for a continuous task.
```

官方文档口径（[continuous-task](https://developer.huawei.com/consumer/cn/doc/HarmonyOS-Guides/continuous-task)）：

> 从 API version 21 开始，支持一个 UIAbility 同一时刻申请多个长时任务，最多可申请 10 个……
> 对于 API version 20 及之前版本，一个 UIAbility（FA 模型则为 ServiceAbility）同一时刻仅支持申请一个长时任务
> …… 应用在申请长时任务成功后，通知栏会显示与长时任务相关联的消息，**用户删除通知栏消息时，系统会自动停止长时任务**。

（本机设备 API 26，但应用 `targetSdkVersion` 为 24。**更新 2026-10-15 13:17 真机实测**：数组形态可用，
但 `updateBackgroundRunning` 报 `9800005 … The application has **not** applied for a continuous task` ——
因为**当时 TTS 的任务已被系统停掉**（见下方 P0），所以「一任务多类型」尚未取到正面成功样本，
方法侧结论仍以 SDK 原文规则 3 为准。）

## 证据 4：DATA_TRANSFER 在 **10 分钟无进度更新**后被系统取消 → 应用随即被冻结

```
07:56:36.488 resource_schedule_service/CONTINUOUS_TASK:
  [StopContinuousTaskByUserInner:2681] remove task key: 20020278_EntryAbility_9237, because notification remove
07:56:44 起 tick 停（n=122 直到 08:04:19 才补上，elapsed 606s → 1066s，冻结 460s）
08:04:2x aa start 回到前台 → tick 立即恢复（PID 仍 1755，计数器从 122 继续）
```

停表时刻距长时任务申请（07:46:33）**恰好 10 分 03 秒**，与 SDK 里 `BackgroundMode.DATA_TRANSFER` 的原文规则吻合
（见下「SDK 原文规则」第 1 条）：**>10 分钟不更新进度 → 该类型任务被取消**；系统取消的落点日志就是
`because notification remove`（通知随任务一并消失）。**回到前台即解冻，进程未重启、计数器续跑。**

## 证据 5：TTS（AUDIO_PLAYBACK）持有长时任务时息屏 ~50 秒即被冻结

```
08:05:34.749 SourceReaderTts: background task started        # AUDIO_PLAYBACK 申请成功
08:06:02.805 SourceReader: Ability onBackground
08:06:15.2  息屏（ENTER_SCREEN_OFF_STATE）
08:07:03.717 SourceReaderTts: play para=19                   # 音频仍在播（AudioRenderer 有非静音帧）
08:07:04.845 tick n=155 elapsed=1231s                        # 最后一行
08:07:10.700 resource_schedule_service/SUSPEND_MSG:
  [OnStandbyPlaybackInServer:187] [20020278] standby because of being frozen, don't deal
```
之后 13 分钟内 tick 与 `play para=` 均无新增（应用整体冻结，进程未退）。**系统侧日志中没有该
AUDIO_PLAYBACK 任务的 `StopContinuousTask` 记录**，即：任务看起来仍被持有，但应用仍被冻结。

（本轮探针的「停 + 起计时器」两次点击未命中，故此时仍是证据 3 的那条计时器在跑 —— 不影响结论：
计数在息屏 50 秒后停止。）

**冻结前应用已在报 AVSession 错误**（非冻结后才出现），每 10–60 s 一条，持续到冻结前一刻：

```
08:06:23.229 1755 12643 E AVSession: [operator()]SetAVPlaybackState:2 in syncExecutor timeout after err:0
08:06:46.528 1755 12643 E AVSession: [operator()]SetAVPlaybackState:2 in syncExecutor timeout after err:0
```

对应 SDK 明示的两种挂起原因（见下「SDK 原文规则」第 2 条）：`SYSTEM_SUSPEND_AUDIO_PLAYBACK_NOT_USE_AVSESSION`
/ `SYSTEM_SUSPEND_AUDIO_PLAYBACK_NOT_RUNNING`（API 20+）。**即：任务在名义上仍被持有，但系统认为
「没接 AVSession / 没在播」→ 息屏后不再豁免冻结。**（应用侧确实 `createAVSession` + `activate()` 了，
见 `TtsController.ets:576/596`，为何系统仍不认账待查。）

> ⚠️ **附带发现（疑似既有 P0，与 T0.1 无关但更严重）**：本次实测里 TTS 播放中息屏 → **应用 50 秒后被冻结、
> 语音停止**。如果这本机可复现，则「听书息屏后台播放」这条 M5 已验收路径在真机上是坏的（`play para=` 停止推进），
> 需要独立排查（`SetAVPlaybackState` 超时 → AVSession 未被系统认可 → 长时任务被挂起）。

## 证据 4b：10 分钟规则**复现**（无任何人为操作，2026-10-15 13:18→13:36）

同一探针、同一日志路径，起 `DATA_TRANSFER` 后息屏、**全程不碰通知栏**：

```
2026-10-15T05:18:52Z START mode=DATA_TRANSFER / LONG_TASK_OK mode=DATA_TRANSFER
2026-10-15T05:19:02Z tick n=1   elapsed=5s
…                        （严格 5 s 一次，零丢）
2026-10-15T05:29:02Z tick n=122 elapsed=611s     ← 最后一次正常 tick
2026-10-15T05:35:58Z tick n=123 elapsed=1026s    ← 415 秒空档后补上的一拍
（此后应用被杀 / 设备时钟跳变，日志不再增长）
```

要点：

1. **停表时刻 611 秒**（≈10 分钟），与证据 4 的 606 秒一致 ⇒ 「10 分钟无进度更新即取消」是**规则**，
   不是「用户删掉通知」的偶发结果；证据 4 里的 `because notification remove` 更可能是**系统取消时清理通知**的连带记录。
2. 冻结**不是永久**：`elapsed=611s → 1026s` 之间被冻结 415 秒，随后补上一拍（进程还在，只是不再被豁免冻结；
   与证据 4 的「回前台即恢复」一致）。
3. 对 Phase 4 的直接含义：作业**必须**在 ≤10 分钟内更新一次进度（实况窗 live view），否则息屏即被冻；
   单轮 3000 源（c=16 ≈4.4 min）落在窗口内，多轮/超长作业必须分片或持续更新。

## SDK 原文规则（来自本机 SDK 的 `.d.ts`，比网页文档更权威）

`$DEVECO_SDK/default/openharmony/ets/api/@ohos.resourceschedule.backgroundTaskManager.d.ts`：

1. **`DATA_TRANSFER` 有 10 分钟进度约束**（`BackgroundMode.DATA_TRANSFER` 注释）：
   > During data transfer, the application needs to update the progress. **If the progress is not updated for more
   > than 10 minutes, the continuous task of the DATA_TRANSFER type will be canceled.**
   > The notification type of the progress update must be **live view**.
2. **`AUDIO_PLAYBACK` 的挂起原因**（`ContinuousTaskSuspendReason`，@since 20）：
   `SYSTEM_SUSPEND_DATA_TRANSFER_LOW_SPEED = 4` / `SYSTEM_SUSPEND_AUDIO_PLAYBACK_NOT_USE_AVSESSION = 5` /
   `SYSTEM_SUSPEND_AUDIO_PLAYBACK_NOT_RUNNING = 6` —— 即「接了任务但没接 AVSession / 没在播」会被系统
   **挂起**（挂起后不再豁免冻结）。
3. **共存只能靠「一个任务带多种类型」**：
   - `startBackgroundRunning(context, bgModes: string[], wantAgent): Promise<ContinuousTaskNotification>`（**@since 12**）
     —— 注释原文：*"A UIAbility can request only **one** continuous task at a time through this API"*，但
     **`bgModes` 可传多个类型**（"One or more types can be passed"）。
   - `updateBackgroundRunning(context, bgModes: string[]): Promise<ContinuousTaskNotification>`（**@since 12**）
     —— 更新既有任务的类型集合，可把听书中的 `['audioPlayback']` 改成 `['audioPlayback','dataTransfer']`。
   - `startBackgroundRunning(context, request: ContinuousTaskRequest)`（@since 21，**本项目 compileSdk 12 用不了**）
     才支持「一个 Ability 最多 10 个任务并存」；且若多类型里含 dataTransfer，会出**两条通知**，删任一条即整体取消。

→ **对 Phase 4 的直接含义**：
- 「边听书边跑预检」**不要**再调一次 `startBackgroundRunning`（必然 `9800005`），而是**把类型集合更新为两种**；
- 任何可能超过 10 分钟的作业，都必须**周期（≤10 min）更新进度**，且进度通知须为**实况窗（live view）**，
  否则任务会被系统取消；单轮 3000 源预检（c=16，约 4.4 分钟）落在单窗口内，但「全量多轮」必须分片或持续更新进度；
- 不能把「作业存活」寄托在 TTS 的 `AUDIO_PLAYBACK` 上（本机实测该任务息屏后不保命，见证据 5）。

## 复现步骤（约 40 分钟）

1. `make run`（含 `module.json5` 的 `"backgroundModes": ["audioPlayback", "dataTransfer"]`）。
2. 设置页 →「起作业 · DATA_TRANSFER」→ 确认 `T0.1 long task ok` + 通知栏常驻通知。
3. 书架 → 开书 → 底部「听书」→ 确认 `SourceReaderTts: background task started` 与 `play para=` 推进。
4. 此时再点「起作业 · DATA_TRANSFER」→ 复现证据 2 的 `9800005`。
5. `uitest uiInput keyEvent 18` 息屏；期间用
   `hdc shell "hilog -x | grep SourceReader"` 轮询落盘，或事后 `hdc file recv` 探针文件：
   `/data/app/el2/100/base/com.lichtcui.sourcereader/haps/entry/files/t0-1-probe.log`。
6. 复现证据 4：`hdc shell "hilog -x | grep CONTINUOUS_TASK"`（`because notification remove`），
   手动在通知栏删掉那条常驻通知即可复现冻结。

## 结论（A1 判定，2026-10-15）

| 问题 | 结论 | 依据 |
|---|---|---|
| `BackgroundMode.DATA_TRANSFER` 是否存在、能否申请 | **能**（SDK 编译期 + 真机 `LONG_TASK_OK` + 常驻通知） | 证据 1 |
| 能否与 TTS 的 `AUDIO_PLAYBACK` 同时持有（两个任务） | **不能**（`9800005`） | 证据 2 |
| 共存的正解 | **一个任务带多种类型**：`bgModes: string[]` / `updateBackgroundRunning`（@since 12） | SDK 原文规则 3 |
| 息屏能否持续跑 | **能，但 DATA_TRANSFER 受「10 分钟无进度更新即取消」约束**；实测 606 s 连续零丢 tick | 证据 3、4 + SDK 规则 1 |
| 能否靠听书的 `AUDIO_PLAYBACK` 顺带保命 | **不能**：TTS 自己的长时任务约 **24 秒**后即被系统停（`AVSessionNotifyUpdateNotification` 失败 `ret=980000502` → `CancelNotification … id -1` → `HandleOnContinuousTaskStop`）；息屏 50 秒应用即被冻结 | 证据 5 + 新增 P0 证据 + SDK 规则 2 |
| 用户删通知 | 长时任务随通知消失即停止（`because notification remove`） | 证据 4 日志 |

**Phase 4 应采取的设计**（写入 `SPEC-DETECT-JOB.md` §3.6）：
1. 作业持有**自己的长时任务**，且**必须带 `dataTransfer` 类型**；听书进行中时用
   `updateBackgroundRunning(['audioPlayback', 'dataTransfer'])` 合并成**一个**任务，绝不二次 `start`。
2. 进度按 **≤10 分钟**节奏更新（实况窗 live view），并在 UI 上体现「预检进行中 n/总数」；
   单轮 3000 源 ≈4.4 分钟（c=16）落在窗口内，但**多轮/超长作业必须分片**（每片 <10 分钟）或持续更新。
3. **不依赖 TTS 存活**：作业要有自己的保命路径，并把「TTS 息屏被冻结」当独立 bug 处理。
