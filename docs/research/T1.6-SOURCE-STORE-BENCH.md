## 结论

最新一轮真机实测三项均达标：

| 指标 | 判据 | 实测 | 结果 |
|---|---:|---:|---|
| 进书源页 `initSourceStore + listRows` 就绪 | ≤ 300 ms | `init 10 + list 34 = 44 ms`；首帧 `18 ms`，页面到就绪 `62 ms` | 通过 |
| 单条 `setEnabled` / `remove` | ≤ 16 ms，且不全量序列化 | 首次 toggle `10 ms`；10 次中位 `1 ms`、最大 `10 ms`；remove `1 ms`；`jsonSerialize=0` | 通过 |
| `upsertMany` 3000 条单事务 | ≤ 2 s | `477 ms`，`added=3000 updated=0` | 通过 |

16 ms 判据对首次写调度较敏感：前一独立轮次首次 toggle 曾为 `20 ms`，但同轮中位 `2 ms`、remove `1 ms`；
最新轮次首次 toggle 为 `10 ms`。两轮均未出现全量序列化，仍将首次写抖动列为残余风险。

## 实测方法

1. 将临时 JSON 放入设备应用 `filesDir`，点 debug-only 入口；实现校验行数、自然键唯一性、
   同 URL 不同名、多分组和混合 enabled 状态。
2. `exportAll()` 备份当前 13 条书源到 `filesDir/t1.6-sources-backup.json`，写入 `seeding` marker，
   清表后调用一次 `upsertMany(3000)`，记录事务耗时和新增/更新计数。
3. 在同一投影上做一次首次 `setEnabled`、随后 9 次 toggle（合计 10 个样本），再删除同 URL 对中的一条；
   记录首次值、中位数、最大值和 remove 值。该路径不调用页面 `reload()`；静态守卫检查
   `setEnabled` / `remove` 不含 `JSON.stringify`、`exportAll` 或 `replaceAll`。
4. 写入 `seeded` marker 后 force-stop / 启动。启动链路检测到 marker 时推迟 SourceStore 初始化；
   进入书源页，首帧后的 `onAppear()` 测冷 `initSourceStore + listRows`，记录首帧和页面到就绪耗时。
5. 自动 `replaceAll(backup)` 恢复原书源，校验行数、自然键和导出 JSON 与备份逐字符串一致，
   删除 marker 并刷新页面。

## 复跑与残余风险

- 主机临时 JSON 和设备数据文件均不进入仓库；复跑时需重新放置 `/tmp/source-reader-t1.6-3000.json`
  对应内容到设备 `filesDir`，哈希可作为同一数据集的依据。
- marker 用于跨重启衔接：`seeding` 阶段重启会走恢复；`seeded` 阶段重启会做首帧后的冷就绪测量再恢复。
  正常 debug 启动只有在该 marker 存在时才推迟 SourceStore 初始化。
- 首次写可能受设备调度影响偶发超过 16 ms；最新轮通过，前一轮首次样本为 20 ms。稳态中位数为 1–2 ms、
  remove 为 1 ms，且没有全量序列化。
- 本轮只覆盖一台真机的当前系统负载，未覆盖低电量、后台高负载、冷存储压力等极端条件。
